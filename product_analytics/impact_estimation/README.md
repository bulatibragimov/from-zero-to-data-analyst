# Введение в оценку изменений в продукте

## Теория

### Зачем проверять гипотезы перед внедрением?

Для развития продукта по **HADI-циклу** команда генерирует и приоритизирует гипотезы, а потом их проверяет и делает выводы.

**Важно проверять гипотезы перед внедрением изменений**, потому что:

> **Только 1 из 8 гипотез является успешной**

### Последствия отсутствия проверки гипотез

| Риск | Что может произойти |
|------|---------------------|
| **Потеря времени** | Команда тратит ресурсы на неэффективные улучшения |
| **Усложнение продукта** | Добавляется функционал, который не нужен пользователям |
| **Ухудшение показателей** | Изменение может негативно повлиять на метрики |
| **Неправильная оценка** | Команда ошибочно считает свои гипотезы эффективными |

---

## Баланс скорости и качества

При проведении экспериментов важно соблюдать баланс:

| Критерий | Что значит |
|----------|------------|
| **Скорость тестирования** | Эксперименты не должны тормозить изменения в продукте |
| **Сложность реализации** | Слишком сложные эксперименты могут быть невыгодны |

**Цель:** найти оптимальный баланс между скоростью и качеством проверки гипотез.

---

## A/B-тестирование — основной метод проверки гипотез

**A/B-тестирование** — один из наиболее популярных методов проверки гипотез.

### Схема A/B-теста

```
Все пользователи
    ↓
    ├── Группа A (Control)     → Старая версия → Измеряем метрику
    └── Группа B (Test)        → Новая версия  → Измеряем метрику
                                    ↓
                            Сравниваем метрики
                                    ↓
                    Решение: раскатывать или нет
```

### Этапы A/B-тестирования

| Этап | Описание |
|------|----------|
| **1. Разделение на группы** | Пользователей случайным образом делят на контрольную и тестовую группы |
| **2. Внедрение изменения** | Новая версия показывается только тестовой группе |
| **3. Сбор данных** | Измеряем метрики в обеих группах |
| **4. Анализ** | Сравниваем результаты |
| **5. Решение** | Принимаем решение о внедрении |

### Почему A/B-тест — это эффективно?

| Преимущество | Объяснение |
|--------------|------------|
| **Причинно-следственная связь** | Можно утверждать, что изменение повлияло на метрику |
| **Минимальный риск** | Изменение тестируется на ограниченной аудитории |
| **Объективность** | Результаты основаны на данных, а не на мнениях |
| **Измеримость** | Можно точно оценить влияние на метрики |

---

## Когда проводить A/B-тест

### ✅ Когда стоит проводить

| Ситуация | Почему |
|----------|--------|
| Изменение влияет на ключевые метрики | Нужно оценить эффект до внедрения |
| Можно разделить пользователей на группы | Техническая возможность есть |
| Есть гипотеза с чёткой метрикой | Можно измерить результат |

### ❌ Когда A/B-тест не нужен

| Ситуация | Почему |
|----------|--------|
| Исправление критического бага | Нужно быстрое решение |
| Изменение тривиальное | Эффект очевиден |
| Нет возможности разделить пользователей | Технически невозможно |

---

## Связь с HADI-циклом

```
Hypothesis (Гипотеза)
    ↓
Action (A/B-тест) ← мы здесь
    ↓
Data (Сбор данных)
    ↓
Insight (Выводы)
```

**Оценка изменений** — это этап **Action** в HADI-цикле.

---

| **Баланс** | Между скоростью тестирования и сложностью реализации |
| **A/B-тест** | Основной метод проверки гипотез |
| **Группы** | Control (старая версия) и Test (новая версия) |
| **Решение** | На основе сравнения метрик |
